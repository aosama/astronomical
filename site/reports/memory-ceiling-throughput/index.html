Field note R-002 28 November 2026 · first published 13 November 2026 Measured, three runs per row

Memory limit · speed

A 22.9 GB model wrote 48 tokens a second under an 8 GB limit.

The same 35B mixture-of-experts model, with the draft model its package carries, answered a 10,000-token prompt four ways: fully in memory, and under 16 GB, 12 GB and 8 GB memory limits. Reading the prompt took about four seconds every time. Writing the reply slowed as the limit came down, and with 8 GB, what a 16 GB Mac can spare, it still wrote 48 tokens a second.

On 13 November, version 0.2.103 and the model without its draft model wrote 66.5 tokens a second fully in memory, 40.3 under 16 GB and 30.2 under 12 GB. The rows above come from a newer build with the draft model the package carries; the gap is widest under the limits, most likely because a step that checks several drafted tokens reads the experts they share from the SSD only once.

This reply summarises text the model has just read, so the draft model guesses more of its words correctly than in a reply written from scratch. The 39 tokens a second at 8 GB on the home page come from a 2,500-token retelling of a play, which gives the draft model less to go on.

How it was measured

The workload, the build, and the clock.

  • Mac

    Apple M5 Pro with 48 GB of memory.

  • Build

    An optimized development build of the main branch after version 0.2.138 (commit ab516c7), serving through the local API the way any client would.

  • Prompt

    The opening of Romeo and Juliet followed by a request for a detailed summary: 10,178 prompt tokens. The reply was capped at 500 tokens, written at temperature 0.7, and every reply reached the cap.

  • Warmup

    One request of 602 prompt tokens and 50 written tokens before each measured request, which also loads the model.

  • Cache

    The persistent prompt cache was turned off, so no saved prompt work counted as speed.

  • Clock

    Reading the prompt is the time from sending the request to the first streamed token. Writing speed is the 499 tokens after the first divided by the time after it.

  • Memory

    Peak model memory is the peak the app reports for the model's own memory, read after each request.

What it does not show

A limit on a large Mac is not a small Mac.

The limit caps the memory the model itself may use. This Mac had 48 GB, so macOS could keep recently read model files in its own file cache, outside that limit. A Mac with 16 GB has far less room for that, and its SSD reads will be slower than the ones measured here. These rows show how the app behaves under a limit. They do not predict speed on a Mac with that much memory.

The model files had been read earlier in the session, so every row is a warm run. Cold reads from the SSD were not measured. Three runs per row show how much a row moves, not how a different session would come out.

Read it as

A 22.9 GB model stayed under an 8 GB limit and kept writing at a usable speed. Not as a promise for any other Mac, model, or prompt.

Repeat it

Four steps on your own Mac.

  1. In Observatory, download the model from the Models page.
  2. On the Settings page, set Maximum model RAM to the limit you want and press Apply. Turn the prompt cache off and save.
  3. Send a long prompt to /v1/chat/completions on the local API with "stream": true and "max_tokens": 500, after one short warmup request.
  4. Time the first streamed token and the last, and read peak memory on Observatory's Overview page.

Your numbers will differ with your Mac, your SSD, the model and the prompt.
